# Static and media deployment

## Asset types

Dastorkon has three separate classes of files. They have different sources,
lifecycles, and backup requirements and should not be combined in production.

| Files | Purpose | Produced or stored in | Production owner |
| --- | --- | --- | --- |
| Django static files | CSS, JavaScript, fonts, and images used by Django admin and installed Django apps | Collected into `BASE_DIR / "staticfiles"` | Nginx at `/static/` |
| Vite frontend build | The React SPA HTML, bundled JavaScript/CSS, and copied public assets | Built into `frontend/dist/` | Nginx at `/` |
| Django media files | Uploaded or generated restaurant logos, menu-item images, user avatars, and demo images | Stored in `BASE_DIR / "media"` | Persistent storage, exposed by Nginx at `/media/` |

Static files and the frontend build are deployment artifacts: they can be
regenerated from the repository and dependencies. Media files are application
data and cannot be regenerated reliably. Never put media inside `staticfiles/`
or `frontend/dist/`, and never delete media as part of a deployment cleanup.

## Current local behavior

The relevant Django settings are:

```python
STATIC_URL = "static/"
STATIC_ROOT = BASE_DIR / "staticfiles"
MEDIA_URL = "media/"
MEDIA_ROOT = BASE_DIR / "media"
```

With `DEBUG=True`, `config/urls.py` exposes `MEDIA_URL` from `MEDIA_ROOT` for
local use. Django's development staticfiles support handles app/admin assets,
and Vite serves the React source during frontend development while proxying
API, media, and WebSocket requests. The debug media route is not used when
`DEBUG=False`; production media is served by Nginx.

Both `staticfiles/` and `media/` are ignored by Git. `frontend/dist/` is also
ignored because it is generated by the frontend build.

## Production build steps

Install dependencies, then build the frontend from the repository root:

```powershell
Set-Location frontend
npm ci
npm run build
Set-Location ..
```

The Vite configuration uses its default output directory,
`frontend/dist/`. This directory is the React SPA document root; it is not an
input to Django's `collectstatic` command.

Collect Django static files separately:

```powershell
python manage.py collectstatic --noinput
```

This copies Django admin and installed-app static assets into
`BASE_DIR / "staticfiles"`. The directory should be rebuilt for each release
and made readable by Nginx. No custom staticfiles storage is required for this
Nginx-based plan.

`BASE_DIR / "media"` must be persistent across releases and writable by the
Daphne application process when uploads are accepted. It should be stored on a
persistent volume or external media service and included in monitored,
regularly tested backups.

## Example Nginx layout

The paths below are examples. Replace `/srv/dastorkon/app` and `example.com`
with the real release, persistent-storage, and domain values for the selected
host. Daphne is assumed to listen on `127.0.0.1:8000`. The maintained, fuller
Ubuntu example is [deploy/nginx/dastorkon.conf.example](../deploy/nginx/dastorkon.conf.example);
see [Ubuntu production deployment](UBUNTU_DEPLOYMENT.md) for its installation
and permission steps.

```nginx
upstream dastorkon_asgi {
    server 127.0.0.1:8000;
}

server {
    listen 80;
    server_name example.com;

    root /srv/dastorkon/app/frontend/dist;
    index index.html;

    location /static/ {
        alias /srv/dastorkon/app/staticfiles/;
    }

    location /media/ {
        alias /srv/dastorkon/app/media/;
    }

    location /api/ {
        proxy_pass http://dastorkon_asgi;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    location /ws/ {
        proxy_pass http://dastorkon_asgi;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 60s;
    }

    # These HTTP routes are also owned by Django rather than the React SPA.
    location ~ ^/(admin|common|notifications)/ {
        proxy_pass http://dastorkon_asgi;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    # React Router handles frontend routes that are not physical files.
    location / {
        try_files $uri $uri/ /index.html;
    }
}
```

For production, terminate HTTPS at Nginx or the selected platform, redirect
plain HTTP to HTTPS, and expose WebSockets through `wss://`. Configure upload
size limits and file permissions to match the application's requirements.

## Deployment verification

After deploying, verify that:

- Django admin loads its CSS and JavaScript from `/static/`.
- Direct navigation to a nested React route returns `index.html` and renders
  the expected screen.
- API requests under `/api/` reach Daphne.
- WebSockets under `/ws/` connect over `wss://` and receive events.
- Existing media remains available after a new release is deployed.
- New uploads are written to persistent media storage and served at `/media/`.
- Media and PostgreSQL backup/restore procedures are tested, not only scheduled.
